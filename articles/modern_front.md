# 設計手法・基本概念系

### SPA (Single Page Application)

ページ遷移しているように見えて、実際には 1 ページで DOM を差し替えるよう設計する開発手法。React/Next.js/Vue/Nuxt などで構築可能。

### MPA (Multi Page Application)

SPA と逆の概念の開発手法。各ページが独立しており、ページ遷移ごとに HTML を取得する従来型。

### Atomic Design

UI コンポーネントを**小さな単位から大きな単位へ階層的**に組み立てていく手法。
Atoms → Molecules → Organisms → Templates → Pages の 5 階層に分割して設計する。
| 階層 | 用途 | 使用例 |
| ---- | ---- | ---- |
| Atoms（原子） | UI の最小単位。これ以上分解できない部品。 | ボタン、ラベル、アイコンなど |
| Molecules（分子） | Atoms を組み合わせた小さな UI 単位。 | ボタン+アイコン、入力欄+ラベルなど |
| Organism（有機体） | Molecules や Atoms を組み合わせた、まとまった UI セクション。 | ヘッダー（ロゴ+メニュー+ボタン）など |
| Template（テンプレート） | Organisms を配置したレイアウト。 | ダッシュボードレイアウト、商品詳細ページレイアウトなど |
| Pages（ページ） | Templates に実データを入れた最終形態。 | ユーザーが実際に見る画面 |

### Presentational/Container

コンポーネントを「見た目やレイアウト」と「データ取得やロジック」の大きな 2 つの責務に分けて開発を行う手法。

:::message

- Presentational：見た目やレイアウトを担当
- Container：データ取得やロジックなどを担当
  :::

### MVVM（Model-View-ViewModel）

UI とロジックを分離し、保守性・再利用性を高めるためのアーキテクチャパターン。
| 階層 | 用途 | 使用例 |
| ---- | ---- | ---- |
| Model | アプリケーションの状態やビジネスロジックを持つ層。UI に依存せず、どこからでも使いわ回せる。 | DB や API から取得したデータ、バリデーション・計算ロジックなど |
| View | ロジックを持たない UI を司る層。ViewModel が提供する状態を監視し、それに応じて描画を行う。 | React コンポーネント、Vue のテンプレートなど |
| ViewModel | View につなぐための状態管理やイベント処理を行う層。Model からデータを取得し View が使いやすい形に変換なども行う。 | ローディングなどの状態管理、Submit などのボタン処理など |

### MicroFrontend

フロントエンドを“マイクロサービス的”に分割して、複数チーム・複数アプリで独立開発・独立デプロイできるようにするアーキテクチャ手法。
大規模フロントエンド開発や、複数プロダクトをまとめる「スーパーアプリ」などでよく使われる。

:::details 分割手法の例

- **ドメインごと**
  - 例：ユーザー管理 / 課金管理 / 商品管理
- **ページ単位**
  - 例：ホーム、検索、カート、注文履歴
- **ウィジェット単位**
  - 例：プロフィールパネル、通知ドロップダウン

:::

# 描画に関する用語

### CSR（Client-side Rendering）

ブラウザ側（クライアント）で JavaScript によってページを描画する仕組み。
SSR などの概念が現れる前は、React・Vue などの SPA で最も一般的な描画方式であった。

### SSR（Server-side Rendering）

CSR とは異なりサーバー側で HTML を生成してからクライアント側に渡して描画する仕組み。
React / Next.js などのモダンフレームワークで広く使われている。

### SSG（Static Site Generation）

基本概念は SSR と同じだが、HTML 生成自体はプロジェクトをビルドする時のみ実行する仕組み。
頻繁に更新されないコンテンツに対してこの描画手法を用いるのが一般的。

### ISR（Incremental Static Regeneration）

Next.js が独自に持っている SSG の描画機能。設定した時間間隔でコンテンツをリビルドする。
SSG（静的生成）の高速性と SSR（動的レンダリング）の柔軟性を両取りしている。

### Hydration（ハイドレーション）

サーバーが先に HTML を描画し、クライアント側（ブラウザ）がその HTML に JavaScript のイベントや状態を “再接続” してインタラクティブにするプロセスのこと。

:::details なぜ、Hydration が必要なのか？

SSR は以下のような手順で描画を行っている。

1. サーバーが HTML を返す
2. ブラウザがそれを表示（この時点ではただの静的 HTML）
3. JavaScript を読み込み → 既存 HTML を解析 → それに対してイベントや状態を復元

この「3」の作業が Hydration に当たる。

つまり、サーバーが出した HTML はそのままではクリックや動作ができないため、Hydration というプロセスを経ることでインタラクティブ性を担保している。

:::

### Partial Hydration

ページ全体ではなく、インタラクションが必要な箇所だけ Hydration するプロセス。
従来はページ全体を Hydration するため、大規模なプロジェクトで動作が遅くなるといった課題があったが、PartialHydration を利用することでこの課題をある程度解消できる。

### VirtialDOM

実際の DOM（ブラウザが扱う重いツリー）を直接操作するのではなく、軽量な JavaScript のオブジェクトとして DOM を仮想的に保持し、差分だけを本物の DOM に反映させる仕組み。

# CSS 関連の用語

### CSS-in-JS

CSS を JavaScript（または TypeScript）内で記述し、コンポーネント単位でスタイルを管理する手法。現在は Zero Runtime CSS である。

| 主要なライブラリ  | 特徴                                            |
| ----------------- | ----------------------------------------------- |
| styled-components | もっとも有名。テンプレートリテラルで CSS を書く |
| emotion           | 軽量。柔軟性・パフォーマンスが高い              |
| Stitches          | 高速・低コスト設計                              |

### Zero Runtime CSS

ブラウザ上で CSS を生成するための JavaScript を一切含まず、すべての CSS をビルド時に生成しておく仕組みの CSS ライブラリー。

- ランタイムでの JS コスト 0
- Hydration 時の追加処理なし
- SSR/RSC との相性 ◎

といった特徴がある。

:::details なぜ Zero-runtime が重要なのか？
従来の CSS-in-JS には以下のような問題があった

- ブラウザで CSS を生成するための JS が必要
- SSR + Hydration 時に JS 実行コストが高い
- RSC（React Server Components）では相性が悪い
- 大規模アプリだと スタイル計算が遅くなる

これらの課題を解決するために、CSS 生成の JS を持たない Zero Runtime というアプローチが生まれた。
:::

| 主要なライブラリ | 特徴                                                                      |
| ---------------- | ------------------------------------------------------------------------- |
| TailwindCSS      | Zero Runtime CSS のデファクトスタンダード。ユーティリティクラスを事前生成 |
| CSS Modules      | Next.js 組み込みの CSS システム。自動でクラス名をハッシュ化する           |
| vanilla-extract  | TypeScript で型安全な CSS を書く。「動的 CSS」もビルド時解決が可能        |

### Design System

プロダクト全体の UI/UX を統一し、再利用性とスケールを高めるための設計基盤 のこと。
単なるコンポーネント集ではなく、デザイン原則・UI パターン・コード・運用ルールなどを包括した総合ガイド。

::::details 主な DesignSystem を構成する要素

1. Design Tokens（デザイントークン）

デザインの最小単位を変数化したもの
（例：色、余白、タイポグラフィなど）

```json
{
  "color.primary": "#1A73E8",
  "spacing.sm": "8px",
  "font.size.base": "16px"
}
```

<br>

---

2. UI コンポーネント
   Button、Input、Card など一貫した挙動・アクセシビリティ・スタイル を備えたコンポーネント群。

   :::message

   例：ShadcnUI / Chakra UI / MUI / Radix UI

   :::

---

3. コンポーネントパターン（UI パターン）
   フォームの組み合わせ、ナビゲーション、モーダル構造など。複数コンポーネントを組み合わせた “UI パターン”。

---

4. ガイドライン

- アクセシビリティ
- レイアウトルール
- モーションガイド
- アイコンルール
  など

---

5. ドキュメントサイト
   Storybook、Ladle、Chromatic などを使ってコンポーネントとガイドを公開。

::::
